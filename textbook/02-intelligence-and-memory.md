## 2.1. Главный тезис: дорогая модель ≠ умный агент

Наивная стратегия — каждый запрос отправлять во флагманскую (frontier) модель с полным контекстом. По оценке из видео, решение одной задачи так стоит около **$3**. При 1 000 задач в день: $3 × 1 000 × 30 = **$90 000 в месяц** *(оценка автора видео; цена задачи зависит от модели, длины контекста и числа шагов)*.

Большая часть этих денег уходит впустую:

- простой вопрос о цене решает модель в 5–25 раз дешевле;
- в контекст попадает вся база знаний, хотя для ответа нужны два абзаца;
- модель «думает» (thinking) там, где нужно просто вызвать инструмент.

> **Главный тезис главы.** Интеллект агента — это не только модель, но и инфраструктура вокруг неё: **роутинг** (какая модель решает задачу), **retrieval** (какие знания она видит) и **бюджет контекста** (сколько она читает и сколько думает). Хорошая обвязка вокруг средней модели часто обходит голую флагманскую модель и по качеству, и по цене.

```
Запрос ─► [Роутер] ──► какая модель и режим?          (2.2)
             │
             ▼
        [Retrieval] ──► какие знания нужны?             (2.3)
             │
             ▼
        [Память] ──► что мы знаем о госте и о прошлом?  (2.4–2.5)
             │
             ▼
        [Бюджет контекста] ──► что влезет и сколько думать? (2.6–2.7)
             │
             ▼
          Модель
```

## 2.2. Умный роутинг (Router LLM)

Запросы отличаются по сложности на порядки. «Сколько стоит латте?» и «спланируй заказ на офис с ограничениями» не должны обрабатываться одной и той же дорогой моделью.

### Три слоя роутера

| # | Слой | Что делает | Цена ошибки | Код |
|---|---|---|---|---|
| 1 | **Фильтр модальностей** | Определяет тип входа (текст, изображение, аудио) и отсекает модели, которые его не примут | Ноль: детерминированная проверка | [`route`](../code/ch02/router.py#L91-L138 "code:route") |
| 2 | **Классификатор сложности** | Маленькая быстрая модель или ML-классификатор: «простой» → дешёвая модель (SLM), «сложный» → флагманская | Ошибка вниз — плохой ответ; ошибка вверх — переплата | [`Verdict`](../code/ch02/router.py#L64-L67 "code:Verdict") |
| 3 | **Резервный слой (fallback)** | Если классификатор упал, не ответил вовремя или не уверен — детерминированные правила по ключевым фразам, затем модель по умолчанию | Переплата, но не отказ | [`rule_fallback`](../code/ch02/router.py#L80-L86 "code:rule_fallback") |

Почему нужен третий слой: классификатор — ещё один внешний сервис, он может упасть или вернуть низкую уверенность. Запрос пользователя не должен падать вместе с ним (тест [`test_classifier_failure_falls_back_to_rules`](../code/ch02/test_ch02.py#L42-L45 "code:RouterTests.test_classifier_failure_falls_back_to_rules")).

**Модель по умолчанию — флагманская.** Если ничего не известно, безопаснее переплатить, чем дать плохой ответ. Для продукта с жёстким бюджетом решение может быть обратным; важно, что оно принято явно ([`route`](../code/ch02/router.py#L91-L138 "code:route"), параметр `default_tier`).

> **Уточнение к видео.** «За миллисекунды» верно для классического ML-классификатора или поиска по эмбеддингам. Если классификатор — маленькая LLM, это обычно десятки–сотни миллисекунд. Задержку роутера стоит измерять: если он тратит больше, чем экономит, он не нужен.

### Альтернатива: каскад (escalation)

Вместо решения на входе можно сначала отправить запрос в дешёвую модель, проверить ответ (уверенность, валидатор, правило) и только при неудаче передать флагманской *(дополнение к видео)*. Каскад хорош, когда дешёвая модель справляется с большинством запросов и ответ легко проверить. Плохо подходит для длинных диалогов — см. ловушку ниже.

Исследования обучаемых роутеров (RouteLLM, ICLR 2025) показывают, что роутер, обученный на данных о предпочтениях, может более чем вдвое снизить стоимость без заметной потери качества относительно «всё во флагманскую модель» [5].

### Ловушка: переключение модели сбрасывает кэш

В главе 1 мы выяснили, что в цикле агента стоимость определяют входные токены, а кэш промпта удешевляет их примерно в 10 раз. Кэш **привязан к конкретной модели**. Если диалог шёл на флагманской модели, а роутер на 30-м ходу решил «вопрос простой — переключимся на дешёвую», новая модель читает всю историю **без кэша** и записывает её в свой кэш (запись дороже обычного входа).

Пример на условных ценах (флагманская: вход $5, чтение кэша $0,5, выход $25 за 1M; дешёвая: вход $1, запись в кэш $1,25, выход $5):

| Ход с историей 100 000 токенов | Стоимость |
|---|---|
| Остаться на флагманской модели (история из кэша) | ≈ $0,053 |
| Переключиться на дешёвую (вся история без кэша + запись) | ≈ $0,126 |

«Дешёвая» модель обошлась **в 2,4 раза дороже**. При короткой истории (500 токенов) картина обратная: переключение стоит $0,001 против $0,003.

> **Правило.** Решение о смене модели внутри диалога принимается по **стоимости хода** с учётом кэша, а не по прайсу. Роутинг дешевле всего на первом ходу или на новой подзадаче с чистым контекстом.

Функция [`turn_cost`](../code/ch02/router.py#L32-L42 "code:turn_cost") считает стоимость хода, а [`route`](../code/ch02/router.py#L91-L138 "code:route") сравнивает «остаться» и «переключиться» (тесты [`test_cache_aware_stays_on_expensive_model`](../code/ch02/test_ch02.py#L51-L57 "code:RouterTests.test_cache_aware_stays_on_expensive_model") и [`test_short_dialog_switches_to_cheap`](../code/ch02/test_ch02.py#L59-L62 "code:RouterTests.test_short_dialog_switches_to_cheap")).

### Код

```python
decision = route(
    Request("Сколько стоит латте?", current_model="barista-frontier",
            history_tokens=12_000, new_tokens=40),
    models=[SMALL, BIG, VISION],
    classifier=my_small_llm_classifier,   # возвращает Verdict(label, confidence)
    default_tier="frontier",
    min_confidence=0.7,
)
log("route", model=decision.model.name, reason=decision.reason, trace=decision.trace)
```

`reason` (`classifier` | `rules` | `default` | `cache_stay`) и `trace` пишутся в лог каждого запроса: без них невозможно понять, почему запрос ушёл в дорогую модель.

## 2.3. Знания агента: RAG, длинный контекст или гибрид

Модели с окном в 1–2 млн токенов породили соблазн: «положим всю базу знаний в промпт, и RAG не нужен». У обоих подходов есть жёсткие компромиссы.

| Критерий | RAG (Retrieval-Augmented Generation) | Длинный контекст (Long Context) |
|---|---|---|
| **Сложность** | Высокая: чанкинг, эмбеддинги, векторная база, реранкинг, обновление индекса | Минимальная: документ кладётся прямо в промпт |
| **Полнота** | Возможны пропуски, если поиск промахнулся или факт разрезан между чанками | Модель видит документ целиком — хорошо для глобальных вопросов («что противоречит чему?») |
| **Экономика** | Индексация один раз при загрузке + на каждом ходу только найденные фрагменты + инфраструктура | Весь документ читается на каждом ходу; кэш промпта сильно снижает цену повторного чтения, но не до нуля |
| **Качество** | Меньше шума: модели не нужно искать «иголку в стоге сена» — стог уменьшен | Риск **Lost in the Middle**: информацию из середины длинного контекста модели используют хуже [3] |
| **Масштаб** | Любой объём — гигабайты и терабайты | Ограничен окном модели |
| **Задержка** | Поиск — сотни миллисекунд, генерация по короткому контексту быстрая | Время до первого токена растёт с длиной контекста |

### Экономика в цифрах

Документ на 200 000 токенов, диалог из 20 ходов, RAG приносит 3 000 токенов на ход, вход $5 за 1M ([`compare_costs`](../code/ch02/retrieval.py#L129-L142 "code:compare_costs"), тест [`test_long_context_vs_rag`](../code/ch02/test_ch02.py#L104-L110 "code:RetrievalTests.test_long_context_vs_rag")):

| Вариант | Стоимость диалога |
|---|---|
| Длинный контекст без кэша | $20,00 |
| Длинный контекст с кэшем (чтение $0,5 за 1M) | $2,90 |
| RAG (эмбеддинги один раз + 3 000 токенов на ход) | ≈ $0,30 |

Кэш сокращает разрыв примерно с 65 до 10 раз, но не убирает его. Это ответ на частое возражение «с кэшем длинный контекст почти бесплатен».

### Гибрид — производственный стандарт

RAG сужает базу знаний до нескольких тысяч релевантных токенов, а контекстное окно даёт модели достаточно места, чтобы рассуждать над ними целиком. По данным видео, такой гибрид сократил контекст в 4 раза, а задержку — с 70 до 1,5 секунды *(цифры из видео, первоисточник не указан; обратите внимание: 70 → 1,5 с — это снижение примерно на 98%, а не на 90%, как сказано в конспекте)*. Независимый замер Elastic даёт тот же порядок: около 1 секунды для RAG против около 45 секунд при передаче ~1 млн токенов целиком [4].

Исследование Li и соавт. (2024) предлагает ещё один вариант гибрида — **Self-Route**: модель сначала пытается ответить по найденным фрагментам и сама сообщает, если их недостаточно; только тогда запрос уходит в длинный контекст [6].

### Как сделать RAG, который не промахивается

1. **Чанкинг с перекрытием** — факт на границе двух кусков не теряется целиком ([`chunk_text`](../code/ch02/retrieval.py#L37-L55 "code:chunk_text")).
2. **Гибридный поиск** — лексический (BM25) находит точные названия и артикулы, векторный — перефразировки. В коде главы — упрощённый BM25 ([`Index`](../code/ch02/retrieval.py#L58-L86 "code:Index")), в проекте добавляют эмбеддинги и реранкер.
3. **Бюджет на знания** — блок знаний собирается жадно по релевантности, пока влезает в выделенный бюджет ([`assemble`](../code/ch02/retrieval.py#L101-L116 "code:assemble")).
4. **Раскладка «по краям»** — против Lost in the Middle самое релевантное кладут в начало и конец блока, слабое — в середину ([`edge_order`](../code/ch02/retrieval.py#L89-L98 "code:edge_order")).
5. **Источник у каждого фрагмента** — `[menu#3]`: модель может сослаться, а вы — проверить.
6. **Найденное — недоверенный ввод** — проходит фильтр из главы 1 (этап 5, непрямые инъекции).

### Чек-лист выбора

- Документ один, небольшой, вопросы глобальные («сравни разделы»)? → длинный контекст с кэшем.
- База большая, вопросы точечные («сколько стоит», «как вернуть деньги»)? → RAG.
- База большая, но вопросы требуют рассуждения над несколькими фрагментами? → гибрид.
- Не уверены? → начните с длинного контекста на прототипе, измерьте цену и задержку, переходите к RAG, когда цифры заставят.

## 2.4. Четыре типа памяти агента (CoALA)

Слово «память» в агентах означает очень разные вещи. Фреймворк **CoALA** (*Cognitive Architectures for Language Agents*, Sumers, Yao, Narasimhan, Griffiths, Принстон, 2023) [2] разделяет её на рабочую и три вида долговременной памяти — по аналогии с когнитивными архитектурами из когнитивной науки (Soar, ACT-R).

> **Уточнение к видео.** Аналогия CoALA — когнитивные архитектуры, а не архитектура компьютера. Сравнение «контекст = RAM, внешнее хранилище = диск» пришло из другой работы — MemGPT (ныне Letta). Обе аналогии полезны, но не стоит их смешивать.

| Тип | Вопрос | Что хранит | Когда меняется | Где в контексте | Barista Agent | Код |
|---|---|---|---|---|---|---|
| **Процедурная** (Procedural) | *Как делать?* | Системный промпт, описания инструментов; в CoALA — также код агента и веса модели | Редко, разработчиком, между релизами | В самом начале — статичный, кэшируемый префикс | Правила «перед `create_order` покажи цену» | [`Procedural`](../code/ch02/memory.py#L26-L33 "code:Procedural") |
| **Семантическая** (Semantic) | *Что знаю?* | Факты о мире и предметной области: база знаний, RAG, справочники | При обновлении базы | Блок знаний текущего хода | Меню, состав, правила возврата | [`Index`](../code/ch02/retrieval.py#L58-L86 "code:Index") |
| **Эпизодическая** (Episodic) | *Что было?* | Конкретные эпизоды, ошибки и извлечённые уроки | Пополняется после действий, читается перед ними | Блок «уроки» текущего хода | «После жалобы на аллергию — уточнять молоко» | [`Episode`](../code/ch02/memory.py#L47-L59 "code:Episode") |
| **Рабочая** (Working) | *Что сейчас?* | Контекст текущей задачи: сообщения, результаты инструментов, план | На каждом ходу | Растущая история сессии | Текущий диалог о заказе | [`Working`](../code/ch02/memory.py#L62-L68 "code:Working") |

Предпочтения гостя («овсяное молоко») формально — семантические факты о пользователе, но технически их удобно хранить так же, как эпизодическую память: файлы с заголовками, которые выбираются под запрос (раздел 2.5).

### Эпизод как запись

Эпизодическая память полезна, только если урок можно применить. Формат записи:

```
[Контекст] гость упомянул аллергию на лактозу
[Действие] агент предложил латте на обычном молоке
[Результат] жалоба
[Урок]     если гость упоминает аллергию или диету — уточнять тип молока до create_order
[Источник] session 2026-10-12 / message 14
```

Источник (якорь происхождения) обязателен: без него нельзя проверить урок, исправить его или удалить, если он оказался ложным. Подробнее о дисциплине записи и отравлении памяти — глава 6.

### Порядок в контексте

Принцип главы 1 «статичное — в начало, динамичное — в конец» определяет место каждого типа:

```
┌─ system ──────────────────────────────┐  процедурная: не меняется → кэшируется
│ роль, правила, инструменты            │
├─ история сессии ──────────────────────┤  рабочая: только дописывается → кэшируется
│ user / assistant / tool ...           │
├─ блок этого хода ─────────────────────┤  меняется каждый ход → в самом конце
│ <knowledge> найденное в RAG           │  семантическая
│ <memory>    предпочтения гостя        │
│ <lessons>   уроки                     │  эпизодическая
└───────────────────────────────────────┘
```

Функция [`build_context`](../code/ch02/memory.py#L218-L236 "code:build_context") собирает контекст именно так; тест [`test_context_static_first_dynamic_last`](../code/ch02/test_ch02.py#L184-L190 "code:MemoryTests.test_context_static_first_dynamic_last") проверяет, что смена найденных знаний не меняет префикс.

## 2.5. Практический разбор: память Claude Code

Хорошо задокументированных промышленных систем памяти мало. В видео разбирается архитектура Claude Code по материалам **утечки исходного кода**: 30–31 марта 2026 года в npm-пакет Claude Code 2.1.88 по ошибке попал source map, из которого восстановили около 512 000 строк TypeScript. Anthropic назвала это ошибкой упаковки релиза, а не взломом; данные пользователей не пострадали [7].

> **Статус сведений.** Ниже — разбор автора видео и публичных обзоров утёкшего кода, а не официальная документация. Детали (имена модулей, лимиты, выбор моделей) могли измениться или находиться за флагами. Используйте их как **архитектурные паттерны**, а не как спецификацию. Автор говорит об 11 подсистемах памяти; здесь разобраны ключевые.

### Паттерн 1. Граница статического и динамического

Системный промпт разделён маркером на две части [8]:

- **статическая** (сверху) — правила, стиль, описания инструментов; одинакова для всех пользователей, поэтому кэшируется максимально широко;
- **динамическая** (снизу) — `CLAUDE.md` проекта, индекс памяти `MEMORY.md`, сжатое резюме сессии, состояние окружения.

Это промышленная реализация правила главы 1 и порядка из раздела 2.4.

### Паттерн 2. Индекс памяти + выбор по заголовкам

`MEMORY.md` — короткий индекс (по обзорам, до ~200 строк и ~25 КБ), который грузится всегда и содержит только указатели. Сами файлы памяти грузятся по необходимости. Выбор делает **отдельный дешёвый вызов модели**, который видит только список «имя файла + однострочное описание» и возвращает до 5 файлов — без эмбеддингов и векторной базы [9].

Ключевое свойство — **prefetch не блокирует основной запрос**: выбор памяти запускается в фоне, пока идёт остальная подготовка.

В коде главы: [`start_prefetch`](../code/ch02/memory.py#L77-L92 "code:start_prefetch") запускает выбор и сразу возвращает `Future`; [`collect_prefetch`](../code/ch02/memory.py#L95-L102 "code:collect_prefetch") забирает результат с таймаутом — не успел, значит этот ход идёт без памяти, а не ждёт. Код также защищается от ответа модели: выдуманные имена и дубликаты отбрасываются, лимит в 5 файлов соблюдается в коде, а не в промпте (тесты [`test_prefetch_limits_and_filters`](../code/ch02/test_ch02.py#L117-L121 "code:MemoryTests.test_prefetch_limits_and_filters"), [`test_prefetch_does_not_block`](../code/ch02/test_ch02.py#L123-L132 "code:MemoryTests.test_prefetch_does_not_block")).

### Паттерн 3. Фоновый агент записи

После ответа пользователю запускается отдельный агент, который читает свежие сообщения, извлекает факты и уроки и записывает их в память. Он хранит **курсор** — до какого сообщения уже обработано — и работает по принципу **at-least-once**: курсор сдвигается только после успешной записи [9].

Следствие, которое легко упустить: при сбое между записью и сдвигом курсора те же сообщения обработаются повторно. Значит, **запись должна быть идемпотентной** — иначе в памяти накопятся дубликаты уроков.

В коде: [`EpisodicWriter`](../code/ch02/memory.py#L110-L152 "code:EpisodicWriter") пишет в append-only журнал (JSONL), каждой записи даёт ключ идемпотентности ([`Episode.key`](../code/ch02/memory.py#L56-L59 "code:Episode.key")) и сдвигает курсор только после записи. Тесты: [`test_episodic_writer_at_least_once_is_idempotent`](../code/ch02/test_ch02.py#L134-L144 "code:MemoryTests.test_episodic_writer_at_least_once_is_idempotent"), [`test_episodic_cursor_not_advanced_on_failure`](../code/ch02/test_ch02.py#L146-L153 "code:MemoryTests.test_episodic_cursor_not_advanced_on_failure").

### Паттерн 4. Консолидация (autoDream)

Отдельный фоновый процесс периодически «приводит память в порядок»: сливает дубликаты, удаляет противоречия, переводит относительные даты в абсолютные, чистит индекс. По обзорам, он запускается не чаще раза в сутки и после нескольких сессий, работает как отдельный субагент с bash только на чтение, а в опубликованной сборке был выключен флагом [7][8]. Это тема главы 6 (агент-арбитр).

### Что взять себе

| Паттерн | Зачем | Где в Barista Agent |
|---|---|---|
| Статика сверху, динамика снизу | Кэш | Системный промпт кофейни отдельно от данных гостя |
| Индекс + выбор по заголовкам | Не грузить всю память | Файлы предпочтений гостей с описаниями |
| Prefetch в фоне с таймаутом | Не платить задержкой за память | Выбор памяти параллельно с RAG по меню |
| Запись после ответа, курсор, идемпотентность | Не тормозить ответ, не плодить дубли | Уроки из жалоб |
| Периодическая консолидация | Память не деградирует | Еженедельная чистка уроков |

## 2.6. Бюджет контекста: лестница сжатия (compaction)

Рабочая память растёт с каждым ходом. Когда контекст приближается к лимиту окна (или к экономическому лимиту), его нужно сжимать. Принцип тот же, что у пайплайна: **сначала дешёвые и безопасные шаги, потом дорогие и с потерей информации**.

| Уровень | Что делает | Потери | Влияние на кэш | Код |
|---|---|---|---|---|
| 1. **Вынос результатов на диск** (offload) | Большой результат инструмента сохраняется в файл; модели — начало (в разборе — первые ~2 КБ) и путь к файлу | Нет: модель может прочитать файл | Нет: применяется к новому результату до того, как он попал в историю | [`compact`](../code/ch02/memory.py#L174-L213 "code:compact") |
| 2. **Микрокомпакт** (microcompact) | Содержимое старых результатов инструментов заменяется заглушкой; последние сообщения не трогаются | Малые: старые результаты обычно уже использованы | Меняет середину истории — кэш после точки изменения пересчитывается *(в видео утверждается, что сброса нет; см. уточнение)* | там же |
| 3. **Автокомпакт** (autocompact) | Старая часть истории заменяется структурированным резюме, последние сообщения сохраняются | Заметные: детали теряются | Полный сброс кэша истории | там же |

Тесты: [`test_offload_keeps_head_and_path`](../code/ch02/test_ch02.py#L155-L163 "code:MemoryTests.test_offload_keeps_head_and_path"), [`test_compaction_ladder_escalates`](../code/ch02/test_ch02.py#L165-L173 "code:MemoryTests.test_compaction_ladder_escalates"), [`test_autocompact_when_micro_not_enough`](../code/ch02/test_ch02.py#L175-L182 "code:MemoryTests.test_autocompact_when_micro_not_enough").

> **Сколько уровней: 3 или 5?** В видео заявлено пять уровней сжатия, в конспекте описаны три. По публичным обзорам утёкшего кода, после автокомпакта есть ещё полное сжатие разговора с повторной загрузкой недавно открытых файлов (до ~5 000 токенов на файл), активного плана и навыков [7], а также аварийная реакция на ошибку «промпт слишком длинный». Состав уровней 4–5 — реконструкция; сверьте с видео.

> **Уточнение про кэш при микрокомпакте.** Изменение середины контекста по определению инвалидирует кэш после точки изменения (глава 1). «Без сброса кэша» микрокомпакт возможен, только если провайдер поддерживает редактирование контекста на своей стороне или если чистятся результаты, которые и так уже выпали из кэша (истёк TTL). Проверяйте по метрике cache hit rate, а не по описанию.

### Правила резюме

Плохое резюме хуже никакого: агент «забывает», что уже оплатил заказ, и оплачивает снова. Резюме должно сохранять:

- цель задачи и текущий план;
- **принятые решения и выполненные необратимые действия** (id заказа, сумма);
- открытые вопросы и ошибки;
- ссылки на файлы с вынесенными данными.

## 2.7. Thinking Mode: когда думать, а когда делать

Режим рассуждений (thinking / reasoning) заставляет модель сгенерировать цепочку рассуждений перед ответом. Токены рассуждений **оплачиваются как выходные**, а выходные у Anthropic стоят в 5 раз дороже входных (у других провайдеров соотношение другое — проверяйте прайс).

Цикл агента естественно делится на фазы:

| Фаза | Итерации | Что происходит | Thinking |
|---|---|---|---|
| **Планирование** | первые 1–2 | Разобрать задачу, учесть ограничения, выбрать инструменты | Включён |
| **Исполнение** | дальше | Вызвать инструмент по плану, передать результат | Выключен |
| **Перепланирование** | после ошибки | Понять, что пошло не так | Включён ненадолго |

Пример: заказ на офис «15 человек, трое без лактозы, до 5 000 ₽». Первая итерация — подумать: разложить по типам напитков, посчитать бюджет. Дальше — `get_menu`, `create_order` × N: думать не о чем, нужно исполнять.

[`ThinkingPolicy`](../code/ch02/router.py#L143-L156 "code:ThinkingPolicy") выдаёт бюджет рассуждений по номеру итерации: полный на фазе планирования, ноль на исполнении, половину после ошибки (тест [`test_thinking_policy`](../code/ch02/test_ch02.py#L68-L71 "code:RouterTests.test_thinking_policy")).

Роутер и политика рассуждений решают вместе: простой вопрос → дешёвая модель без thinking; сложная задача → флагманская модель с thinking на планировании.

> **Нюанс.** Некоторые провайдеры требуют сохранять блоки рассуждений в истории при работе с инструментами, а переключение режима посреди хода может сбросить кэш. Меняйте режим на границе итераций и проверяйте документацию провайдера.

## Итоги главы

1. Дорогая модель ≠ умный агент. «Всё во флагманскую модель с полным контекстом» — это порядка $3 за задачу и $90 000 в месяц на 1 000 задач в день.
2. Роутер — три слоя: модальности → классификатор → правила и модель по умолчанию. Классификатор может упасть — запрос не должен.
3. Смена модели внутри диалога сбрасывает кэш; решайте по стоимости хода, а не по прайсу.
4. RAG и длинный контекст — не конкуренты: стандарт — гибрид. Кэш удешевляет длинный контекст, но не делает его бесплатным.
5. Четыре типа памяти (CoALA): процедурная, семантическая, эпизодическая, рабочая — у каждой свой жизненный цикл и своё место в контексте.
6. Память читается в фоне с таймаутом и пишется в фоне после ответа; at-least-once требует идемпотентной записи.
7. Сжатие контекста — лестница от дешёвых шагов к дорогим; резюме обязано сохранять необратимые действия.
8. Thinking — на планировании, не на исполнении.

## Практикум: Barista Agent v0.2

Базовый код — `code/ch02/`. Каждое задание сопровождается тестом.

1. **Запуск.** Прогоните `python -m unittest test_ch02.py -v`, найдите для каждого теста раздел главы.
2. **Классификатор на LLM.** Напишите классификатор для [`route`](../code/ch02/router.py#L91-L138 "code:route") на дешёвой модели вашего провайдера: промпт из 5–10 примеров, ответ — JSON `{"label": ..., "confidence": ...}`. Соберите 50 размеченных запросов к кофейне и измерьте точность и задержку.
3. **Каскад.** Реализуйте альтернативу роутеру: дешёвая модель → валидатор ответа → при неудаче флагманская. Сравните стоимость и качество на тех же 50 запросах.
4. **Реальные цены.** Заполните [`ModelSpec`](../code/ch02/router.py#L21-L29 "code:ModelSpec") актуальными ценами двух моделей провайдера и найдите длину истории, после которой переключение на дешёвую модель перестаёт окупаться.
5. **Векторный поиск.** Добавьте к [`Index`](../code/ch02/retrieval.py#L58-L86 "code:Index") поиск по эмбеддингам и объедините результаты (Reciprocal Rank Fusion). Найдите запрос, на котором BM25 промахивается, а гибрид — нет.
6. **Self-Route.** Реализуйте гибрид из [6]: модель отвечает по найденному или возвращает «недостаточно данных» — тогда запрос уходит с полным документом. Посчитайте долю запросов каждого типа.
7. **Уроки в контексте.** Подключите [`EpisodicWriter`](../code/ch02/memory.py#L110-L152 "code:EpisodicWriter") к циклу из главы 1: после каждой сессии извлекайте уроки дешёвой моделью, перед каждой — подставляйте 3 самых релевантных.
8. **Резюме, которое не теряет заказ.** Напишите `summarize` для [`compact`](../code/ch02/memory.py#L174-L213 "code:compact") и тест: после автокомпакта в резюме есть id всех оплаченных заказов.
9. **Thinking в цикле.** Подключите [`ThinkingPolicy`](../code/ch02/router.py#L143-L156 "code:ThinkingPolicy") к `run_agent` из главы 1 и сравните стоимость задачи «заказ на офис» с thinking на всех итерациях и только на планировании.

## Глоссарий

| Термин | Значение |
|---|---|
| **At-least-once** | Гарантия доставки «минимум один раз»: при сбое возможна повторная обработка, поэтому получатель должен быть идемпотентным |
| **BM25** | Классический алгоритм лексического поиска: ранжирует документы по совпадению слов с учётом их редкости |
| **Chunking (чанкинг)** | Нарезка документов на фрагменты для индексации и поиска |
| **CoALA** | Cognitive Architectures for Language Agents — фреймворк, раскладывающий агента на память, действия и цикл принятия решений |
| **Compaction (сжатие)** | Уменьшение рабочего контекста: вынос, очистка, резюмирование |
| **Embeddings (эмбеддинги)** | Векторные представления текста для поиска по смыслу |
| **Fallback** | Резервный путь на случай отказа основного |
| **Frontier-модель** | Флагманская модель переднего края: самая способная и самая дорогая |
| **Idempotency (идемпотентность)** | Повторное выполнение операции даёт тот же результат, что и однократное |
| **Lost in the Middle** | Эффект: модели хуже используют информацию из середины длинного контекста |
| **Prefetch** | Заблаговременная загрузка данных параллельно с основной работой |
| **Prompt caching / KV-кэш** | Повторное использование обработанного префикса контекста; привязан к конкретной модели |
| **RAG** | Retrieval-Augmented Generation — поиск релевантных фрагментов и добавление их в контекст |
| **Reranker (реранкер)** | Модель, переупорядочивающая найденные фрагменты по релевантности |
| **Router (роутер)** | Компонент, выбирающий модель и режим под запрос |
| **SLM** | Small Language Model — маленькая быстрая модель для простых задач |
| **Thinking / reasoning tokens** | Токены рассуждений модели перед ответом; оплачиваются как выходные |
| **TTFT** | Time To First Token — задержка до первого токена ответа |

## Модуль 1. Введение и архитектурный пайплайн AI-агента

### 1.1. Фундаментальное различие: Workflow vs. Agent Loop
Многие разработчики совершают ошибку, воспринимая создание AI-агента как написание нескольких строк кода с вызовом LLM. В реальной производственной среде системы делятся на две принципиальные категории [1, 4]:

* **Workflow (Детерминированный конвейер)**: Разработчик строго фиксирует последовательность шагов в коде ($Step_1 ightarrow Step_2 ightarrow Step_3$). Языковая модель (LLM) выполняет трансформации внутри конкретного шага, но **не принимает решений о выборе следующего маршрута**. 
  * *Плюсы*: Полная предсказуемость, минимальная стоимость, низкая задержка (latency), абсолютный контроль.
  * *Область применения*: Классификация писем, форматирование данных, генерация отчетов по шаблону.
* **Agent Loop (Автономный цикл)**: Модели передается цель и набор инструментов (Tools). LLM на каждом шаге сама анализирует текущее состояние контекста, решает, какой инструмент вызвать, получает результат выполнения инструмента и повторяет цикл до достижения цели.
  * *Плюсы*: Высокая гибкость в условиях высокой неопределенности.
  * *Риски*: Высокая стоимость, непредсказуемость времени выполнения, риск бесконечных зацикливаний и галлюцинаций.

> **Золотое правило инженерии**: *Увеличивайте автономию системы только тогда, когда детерминированный Workflow не справляется с вариативностью задачи [5].*

---

### 1.2. 6 этапов универсального конвейера (Pipeline)
Универсальная архитектура обработки запроса строятся на принципе: **«Блокируй рано, трать поздно»** — дешёвые проверки выполняются в первую очередь, а дорогостоящий вызов LLM происходит в самом конце [19, 26].

```
[Входной запрос] 
       │
       ▼
1. Validation Stage (Формат, длина, регулярные выражения) ──► Fail Fast (0$)
       │
       ▼
2. Security Gate (Input Prompt Injection / Sanitization) ──► Блокировка атак
       │
       ▼
3. Context Enrichment & Retrieval (RAG, Семантическая и Эпизодическая память)
       │
       ▼
4. Context Assembly & Budgeting (Сборка системного промпта, сжатие, KV-Cache optimization)
       │
       ▼
5. Generation Stage (Вызов LLM / Agent Loop / Reasoning Mode)
       │
       ▼
6. Postprocessing & Output Validation (Schema check, PII filter, Canary tokens) ──► [Ответ пользователю]
```

1. **Validation Stage (Валидация)**: Проверка базовой корректности входной строки (длина, отсутствие бинарного мусора, поддерживаемый язык). Отсекает до 5% сорного трафика с нулевыми затратами [19].
2. **Security Gate (Входная безопасность)**: Проверка на прямой и непрямой Prompt Injection до обращения к векторным базам и LLM [20]. *(Подробнее см. [Модуль 7.1](#71-многоуровневая-безопасность-defense-in-depth-и-избыточная-автономия)).*
3. **Context Enrichment & Retrieval (Обогащение контекста)**: Подтягивание пользовательских предпочтений, актуального состояния среды, вызов RAG и поиск по семантической памяти [21].
4. **Context Assembly & Token Budgeting (Сборка контекстного окна)**: Жесткое бюджетирование токенов. Структура промпта строится с учетом сохранения KV-Cache (добавление новых данных строго в конец контекста) [23, 29, 30].
5. **Generation Stage (Генерация / Исполнение)**: Выполнение запроса выбранной моделью или запуск автономного цикла.
6. **Postprocessing & Output Validation (Постпроцессинг)**: Валидация вывода по JSON Schema, маскирование PII (персональных данных) и проверка на утечку системного промпта [25].

### 1.3. Анатомия и защита автономного цикла (Agent Loop)
Сердцем автономного агента является цикл ReAct (Reason + Act). Однако необработанный цикл без жестких программных ограничений представляет собой системную угрозу [32]:

#### Ключевые риски незащищенного Agent Loop:
* **Зацикливание (Infinite Loop)**: Агент выполняет один и тот же инструмент с одинаковыми аргументами десятками раз подряд (например, 58 повторных вызовов одного API) [32].
* **Взрывной рост стоимости (Token Cost Explosion)**: На каждой итерации цикла агент перечитывает все предыдущие шаги. Контекстное окно растет линейно, а суммарная стоимость — квадратично [28, 33].
* **Накопление галлюцинаций (Hallucination Cascade)**: Ошибка или галлюцинация на шаге $N$ принимается агентом за несомненный факт на шаге $N+1$, приводя к катастрофическим последствиям [33].

#### 4 обязательных барьера безопасности в коде (In-Code Invariants):
1. **Max Iteration Limit**: Жесткое ограничение количества итераций цикла (например, макс. 5 для саппорта, макс. 25 для кодинг-агента) [34].
2. **Token Budget Cap**: Потолок суммарно потраченных токенов на задачу.
3. **Tool Call Duplication Limit**: Запрет на повторный вызов одного и того же инструмента с идентивными параметрами [34].
4. **Human-in-the-Loop Gate**: Принудительная остановка цикла и запрос подтверждения человеком перед выполнением необратимых действий (удаление, проведение транзакции, изменение прав) [35]. *(См. также [Модуль 4.4](#44-трехуровневая-верификация-инвариантов)).*

## Модуль 2. Архитектура интеллекта и памяти AI-агента

### 2.1. Классификация 4 типов памяти по фреймворку Coalla
В соответствии с когнитивной архитектурой Coalla (Princeton), память AI-агента разделяется на 4 специализированных слоя с различным жизненным циклом [60]:

```
+-------------------------------------------------------------------------+
|                                AI AGENT MEMORY                          |
+--------------------+--------------------+-------------------------------+
| Процедурная        | Семантическая      | Эпизодическая                 | Рабочая                       |
| (Procedural)       | (Semantic)         | (Episodic)                    | (Working)                     |
+--------------------+--------------------+-------------------------------+-------------------------------+
| System Prompt,     | Базы знаний, RAG,   | Дневник уроков, прошлый опыт  | Текущее контекстное окно,     |
| Инструкции тулов   | Факты о проекте    | успехов и ошибок (Invariants) | состояние активной задачи     |
| Меняется редко     | Накапливается      | Обогащает действия контекстом | Очищается после завершения    |
+--------------------+--------------------+-------------------------------+-------------------------------+
```

1. **Процедурная память (Procedural Memory)**: Знание того, *как выполнять задачи*. Включает системный промпт, правила валидации, контракты вызова инструментов. Изменяется разработчиком между сессиями [60].
2. **Семантическая память (Semantic Memory)**: Знание *фактов и мира*. Представляет собой внешние базы знаний, векторные хранилища (RAG) и документацию [60].
3. **Эпизодическая память (Episodic Memory)**: Опыт *прошлых действий и уроков*. Хранит записи вида: `[Контекст] -> [Действие] -> [Результат] -> [Извлеченный урок]`. Позволяет агенту не повторять вчерашние ошибки [61, 62]. *(Изучите реализацию в [Модуле 6.3](#63-фоновый-агент-арбитр-wikigroomer-и-борьба-с-концепт-дрифтом)).*
4. **Рабочая память (Working Memory)**: Оперативный контекст текущей задачи. Ограничена размером контекстного окна и полностью очищается/суммаризируется по завершении сессии [63].

### 2.2. Сравнительный анализ: RAG vs. Длинное контекстное окно
С появлением моделей с контекстным окном в 1-2 млн токенов возникло заблуждение, что RAG больше не нужен. Инженерный анализ показывает жесткие компромиссы [52-56]:

| Критерий | RAG (Retrieval-Augmented Generation) | Long Context Window (1M+ токенов) |
| :--- | :--- | :--- |
| **Сложность инфраструктуры** | Высокая (векторные базы, чанкинг, эмбеддинги, реранкинг) [53] | Минимальная (загрузка всего файла напрямую в промпт) [53] |
| **Стоимость эксплуатации** | Низкая (оплата только релевантных чанков) [54] | Экспоненциальная (перечитывание огромного текста на каждом шаге) [54] |
| **Точность локального поиска** | Высокая (извлечение точных «иголок» без шума) [55] | Уязвима к эффектам *Lost in the Middle* и *Context Erosion* [55, 123] |
| **Полнота глобального анализа** | Риск упустить связи при разрыве чанков [53] | Абсолютная (модель видит весь документ целиком) [54] |

> **Производственный стандарт**: Гибридный подход. RAG используется для первичной фильтрации базы знаний из гигабайт до десятков тысяч токенов, которые затем подаются в контекст для глубокого рассуждения [56, 57].

---

### 2.3. Стратегическое мышление (Thinking Mode) и бюджетирование токенов
Режим глубокого рассуждения (Thinking / Reasoning Mode) генерирует внутреннюю цепочку мыслей перед выдачей ответа.

* **Экономический фактор**: Токены рассуждения (Thinking Tokens) тарифицируются как *выходные токены*, которые стоят в **4–5 раз дороже входных** [76].
* **Динамический Reasoning**:
  * Простые семантические запросы («Сколько стоит доставка?») $ightarrow$ *Thinking Disabled* (Дешёвая модель) [77].
  * Сложный архитектурный анализ или первичная декомпозиция задачи $ightarrow$ *Thinking Enabled* на первых 1-2 итерациях цикла, с последующим отключением режима для рутинных вызовов инструментов [77]. *(См. [Модуль 3.3](#33-гибридный-роутинг-и-архитектура-классификаторов)).*

## Модуль 3. Экономика и выбор LLM в продакшене

### 3.1. Стратегический выбор: API vs. Self-Hosted (Open-Source)
Выбор между провайдерами API (Anthropic, OpenAI, Google) и собственным хостингом Open-Source моделей (Llama, Qwen, DeepSeek) определяется тремя векторами [225-228]:

```
                         [Требования к регуляции и PII]
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
           [Да / Строгие]                            [Нет / Гибкие]
                 │                                         │
        [Запрет облаков?]                         [Расчет TCO & Масштаб]
           ┌─────┴─────┐                             ┌─────┴─────┐
           ▼           ▼                             ▼           ▼
      [Self-Host]  [Enterprise API]             [Self-Host]    [API]
```

1. **Регуляторные ограничения (Data Privacy)**: При наличии требований ФЗ/GDPR/HIPAA и невозможности использования изолированных Enterprise VPC — выбор однозначно за Self-Host [225, 226].
2. **Нагрузка и паттерн трафика**: На малых и средних объемах API всегда дешевле за счет отсутствия простоев выделенного GPU [226].
3. **Потребность в тонкой настройке (Fine-tuning)**: Если под узкий домен требуется специфический формат вызова инструментов или специальный язык, выигрывает Open-Source.

---

### 3.2. Расчет совокупной стоимости владения (TCO)
При сравнении стоимости **нельзя сравнивать только цену токенов API со стоимостью аренды GPU** [232]. Реальная формула TCO для Self-Hosted включает 4 компонента:

$$	ext{TCO}_{	ext{Self-Host}} = 	ext{Cost}_{	ext{GPU}} + 	ext{Cost}_{	ext{Infra}} + 	ext{Cost}_{	ext{DevOps/SRE}} + 	ext{Cost}_{	ext{Complexity}}$$

* **Cost GPU**: Прямая аренда карт (A100/H100) или кластеров.
* **Cost Infra**: Трафик, хранилище для весов и векторных БД.
* **Cost DevOps/SRE**: Зарплатные часы высококвалифицированных инженеров на настройку vLLM/TGI, оптимизацию квантования и поддержку SLA 99.9% [232]. *Часто эта статья в 5-10 раз превышает арендную плату за GPU.*
* **Cost Complexity**: Издержки от задержки выкатки новых фич.

---

### 3.3. Гибридный роутинг и архитектура классификаторов
Для оптимизации затрат без потери качества применяется **гибридная архитектура роутинга** (Router LLM) [46, 237]:

```
[Запрос пользователя] ──► [Классификатор (Small Model / Fast Classifier)]
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
 [Простой запрос]          [Средняя сложность]       [Сложный / Критичный]
  Llama-3-8B / Flash         Claude 3.5 Sonnet         Claude 3.5 Sonnet / Opus
   (Стоимость: 1x)            (Стоимость: 15x)          (Стоимость: 50x+)
```

1. **Классификатор (Router)**: Ультрабыстрая модель (1B-3B параметров) за миллисекунды оценивает сложность входящего запроса [48].
2. **Таблицы маршрутизации**: Простые CRUD-операции и стандартные вопросы направляются на локальные/дешёвые модели. Многошаговое рассуждение и генерация кода — на топовые фронтир-модели [46].
3. **Учет KV-Cache при роутинге**: Внимательно отслеживайте смену моделей внутри одного диалога. Переключение модели посреди длинного чата инвалидирует KV-кэш предыдущей модели, что ведет к повторным затратам [49, 50].

## Модуль 4. Harness Engineering: проектирование среды исполнения

### 4.1. Парадигмальный сдвиг: От промпт-инжиниринга к Harness Engineering
> *«Качество работы агента определяет не столько сама модель, сколько код обвязки (Harness) вокруг неё» [131].*

Промпт-инжиниринг как отдельная дисциплина исчерпал себя. На смену пришел **Harness Engineering** — проектирование надежной среды исполнения, алгоритмов верификации и автоматических обратных связей [133, 152].

```
┌────────────────────────────────────────────────────────────────────────┐
│                        HARNESS ENGINEERING LAYER                       │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────────┐  │
│  │    Constrain     │  │      Inform      │  │        Verify        │  │
│  │ (Ограничения)    │  │ (Информирование) │  │    (Верификация)     │  │
│  └────────┬─────────┘  └────────┬─────────┘  └──────────┬───────────┘  │
│           │                     │                       │              │
│           └─────────────────────┼───────────────────────┘              │
│                                 ▼                                      │
│                      ┌──────────────────────┐                          │
│                      │       Correct        │                          │
│                      │  (Коррекция/Retry)   │                          │
│                      └──────────────────────┘                          │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   ▼
                      [LLM / Двигатель системы]
```

---

### 4.2. 4 управляющие функции (OpenAI Framework)
По фреймворку OpenAI, обвязка агента выполняет 4 ключевые функции [134]:

1. **Constrain (Ограничить)**: Программное установление рамок — жесткие лимиты токенов, списки разрешенных вызовов (allowlists), песочницы исполнения [136].
2. **Inform (Проинформировать)**: Передача контекста, инструкций к инструментам и динамического состояния системы [137].
3. **Verify (Проверить)**: Автоматическая проверка результатов работы агента через инварианты, линтеры и тесты [139, 141].
4. **Correct (Исправить)**: Автоматическое формирование конструктивных сообщений об ошибках и возврат агента на повторную итерацию цикла [133, 140].

---

### 4.3. 7 слоев системной обвязки (Harness Architecture)
Современная производственная обвязка делится на 7 функциональных слоев [160-164]:

1. **Execution Sandbox (Ядро исполнения)**: Изолированная среда (Docker, gVisor, WASM) для выполнения кода и команд агентом [160].
2. **Tooling & Protocols (Инструментальный слой)**: Валидация схем инструментов (JSON Schema, MCP Protocol), обработка тайм-аутов и гармонизация ошибок [161].
3. **Context Manager (Управление контекстом)**: Сборка промпта, отсечение устаревших данных, стратегии уплотнения (Compaction) [162].
4. **Lifecycle & State Machine (Управление жизненным циклом)**: Оркестрация состояний, обработка прерываний, возобновление сессий (Recovery) [162].
5. **Observability Layer (Слой наблюдаемости)**: Сквозное трассирование, метрики, логирование шагов и вызовов [163]. *(См. [Модуль 7.3](#73-сквозная-наблюдаемость-observability-и-5-ключевых-метрик-ai-агентов)).*
6. **Verification Layer (Слой проверки)**: Инварианты в коде, Judge-модели, замеры качества [164].
7. **Governance & Security (Слой безопасности)**: Защита от Prompt Injection, разграничение прав доступа, лимиты суточных бюджетов [164].

---

### 4.4. Трехуровневая верификация инвариантов
Проверка результатов агента выстраивается в иерархию по скорости и стоимости [145]:

```
Level 1: Invariants in Code (0$ / 0ms) ──► Мгновенная проверка детерминированными правилами
Level 2: Benchmark & Evaluation Runs  ──► Периодические запуски на эталонных датасетах
Level 3: Human-in-the-Loop Validation ──► Проверка человеком сложных и рискованных действий
```

* **Level 1: Инварианты в коде (Invariants in Code)**: Мгновенные, бесплатные проверки. *Пример*: Сумма возврата не может превышать сумму заказа; дата релиза не может быть в прошлом [141, 144].
* **Level 2: Замеры на эталонных запросах (Eval Runs)**: Автоматический прогон системных тестов при смене модели или обновлении промптов [140, 145].
* **Level 3: Проверка человеком (Human-in-the-Loop)**: Подтверждение критических действий [146].

## Модуль 5. Мультиагентные системы и архитектурные паттерны

### 5.1. Природа когнитивной перегрузки одиночной модели
Передача единой сложной задачи («Проведи аудит кода, найди баги, перепиши модули, обнови документацию и составь отчет») одной моделью приводит к **когнитивной перегрузке** (Cognitive Overload) [81].
* Модель размывает внимание между десятками инструкций (*Loss of Focus*).
* Возрастает вероятностная ошибка при выборе из большого количества инструментов (при $Tool count > 20$ начинается резкое падение точности) [38, 81].

*Решение*: Разделение труда и специализация — построение мультиагентной команды, где каждый агент обладает узким контекстом и ограниченным набором инструментов [82, 83].

---

### 5.2. 7 ключевых паттернов мультиагентного взаимодействия
В индустрии сформировались 7 фундаментальных архитектурных паттернов [83-90]:

```
1. Pipeline        : [A1] ──► [A2] ──► [A3]
2. Router          : [Router] ──► [A_fast] OR [A_expert]
3. Parallelization : [A_split] ──► [A1] + [A2] + [A3] ──► [Aggregator]
4. Reflection      : [Generator] ◄──► [Critic / Reflector]
5. Tool Use        : [Agent] ──► [Orchestrator] ──► [External APIs]
6. Planning        : [Planner] ──► [Task Graph] ──► [Workers]
7. Collaboration   : [Role A] ◄──► [Role B] ◄──► [Role C] (Shared Environment)
```

1. **Pipeline Pattern (Конвейер)**: Последовательная передача выхода одного агента на вход следующему. *Применение*: Пошаговая обработка документов [83, 84].
2. **Router Pattern (Маршрутизатор)**: Первичный агент определяет категорию задачи и направляет её узкоспециализированному агенту [84, 85].
3. **Parallelization Pattern (Параллелизация)**: Декомпозиция независимых подзадач и их одновременное выполнение с последующей агрегацией. *Применение*: Анализ больших объемов данных [85].
4. **Reflection Pattern (Рефлексия)**: Пара «Генератор — Критик». Критик оценивает вывод генератора по критериям качества и возвращает на доработку до достижения идеала [86, 87].
5. **Tool Use Pattern (Использование инструментов)**: Оркестрация вызовов внешних функций и API с валидацией возвращаемых ответов [87, 88].
6. **Planning Pattern (Планирование)**: Планировщик строит динамический граф задач (Task Graph), который исполняется рабочими воркерами [88, 89].
7. **Collaboration Pattern (Коллаборация)**: Команда агентов с разными ролями (например, Программист, Тестировщик, PM) взаимодействует в общей среде до решения задачи [89, 90].

---

### 5.3. Накладные расходы, антипаттерны и принцип прогрессивной сложности
Переход к мультиагентным системам сопровождается существенными издержками:
* **Рост потребления токенов**: Мультиагентные системы расходуют **в 10–15 раз больше токенов**, чем одиночные агенты [90, 94].
* **Рост задержки (Latency)**: Сетевые вызовы и последовательное согласование между агентами увеличивают время отклика.

#### Антипаттерны применения:
* Использование мультиагентных команд для простых FAQ или линейных задач [93].
* Избыточная координация для систем реального времени [94].

> **Принцип прогрессивной сложности**: *Начинайте с одного агента -> Добавляйте рефлексию -> Внедряйте роутинг -> Переходите к параллелизации и планированию только при исчерпании возможностей предыдущих ступеней [90, 96].*

## Модуль 6. Долговременная память и управление знаниями

### 6.1. Архитектурная развилка: Синтез при записи vs. Синтез при чтении
При проектировании баз знаний для AI-агентов существует фундаментальная развилка [100, 101]:

```
                    [ВХОДЯЩИЕ ДАННЫЕ / ИСТОЧНИКИ]
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
[Синтез при записи (Write-Time)]               [Синтез при чтении (Read-Time)]
- Агент обобщает факты СРАЗУ.                  - Данные сохраняются в СЫРОМ виде.
- Запись дорогая, чтение дешёвое.             - Запись бесплатная, чтение дорогое.
- РИСК: Сжатие с потерями и искажения [101].   - ПЛЮС: Полная сохранность оригинала.
```

---

### 6.2. Дисциплина записи: Append-Only журналы и якоря происхождения
Главная причина «порчи» памяти при наличии нескольких агентов-писателей — перезапись файлов (*Lost Update* / *Write Collisions*) [105].

#### Производственные стандарты дисциплины записи:
1. **Append-Only Log (Журнал только для записи)**: Никакой агент не имеет права редактировать или удалять прошлые записи в БД. Новая информация добавляется строго инкрементально в конец [106, 111].
2. **Якоря происхождения (Source Anchoring)**: Каждая запись в памяти должна содержать привязку к неизменяемому первоисточнику (ID транскрипта, хэш коммита, URL документа, timestamp) [112, 113].

---

### 6.3. Фоновый агент-арбитр (WikiGroomer) и борьба с концепт-дрифтом
Со временем факты в базе знаний устаревают и начинают противоречить друг другу (Концепт-дрифт) [106]. Для поддержания гигиены памяти выделяется специальный фоновый процесс — **WikiGroomer** [115]:

#### Задачи агента WikiGroomer:
1. **Консолидация и дедупликация**: Периодическое прочесывание сырого лога и сборка аккуратных сводок-кэшей [115].
2. **Детекция противоречий**: Нахождение конфликтующих фактов (например, «Используем GitFlow» vs «Перешли на Trunk-Based Development») и их эскалация человеку в командный чат [116].
3. **Версионирование актуальности**: Старые записи не удаляются, а закрываются с проставлением даты упреждения [113, 114].

---

### 6.4. Проблема отравления памяти (Memory Poisoning) и Prompt Injection
Общая память представляет собой поверхность атаки. Если один из агентов прочитал вредоносный сайт или отравленное письмо (Indirect Prompt Injection), он может записать инструкции атаки в общую память [107-109].

#### Защитный принцип «Правило двух условий» (Meta Security):
Опасность возникает при одновременном наличии трех условий:  
1. Доступ к приватным данным.  
2. Недоверенный входной поток.  
3. Канал вывода информации наружу [107].

> **Защита**: Разорвите цепочку, заблокировав канал вывода наружу (Human-in-the-Loop) при контакте агента с немодерируемой памятью [110]. *(См. [Модуль 7.1](#71-многоуровневая-безопасность-defense-in-depth-и-избыточная-автономия)).*

## Модуль 7. Продакшн-эксплуатация: безопасность, отказоустойчивость и наблюдаемость

### 7.1. Многоуровневая безопасность (Defense-in-Depth) и избыточная автономия
Атаки на AI-агентов выходят за рамки обычного веб-безопасности [176-178]:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      DEFENSE-IN-DEPTH ARCHITECTURE                      │
│                                                                         │
│  [Вход] ──► 1. Input Security Gate (Guard Models)                       │
│                   │                                                     │
│                   ▼                                                     │
│             2. Content & RAG Integrity Verification (Hashes & Evals)     │
│                   │                                                     │
│                   ▼                                                     │
│             3. Isolated Execution Sandbox (e.g. gVisor / Docker)        │
│                   │                                                     │
│                   ▼                                                     │
│             4. Output Validation & Action Proxies (Human Gate) ──► [Выход]│
└─────────────────────────────────────────────────────────────────────────┘
```

#### Риск избыточной автономии (Excessive Agency / Confused Deputy):
Ситуация, когда агент обладает полномочиями выполнения опасных команд, но теряет понимание границ в процессе работы [178, 180].

#### Стратегия защиты:
* **Изоляция прав (Least Privilege)**: Агент должен иметь доступ только к микро-токенам с минимально необходимыми правами [183].
* **Программный Proxy**: Проверка опасности тула выполняется внешним кодом прокси-сервера, а не инструкцией в промпте [182].

---

### 7.2. Отказоустойчивость (Resilience): Circuit Breakers, идемпотентность и стратегия ошибок
Производственный агент должен сохранять работоспособность при падении внешних LLM-провайдеров [194, 195]:

1. **Circuit Breaker (Предохранитель)**: При превышении порога ошибок (5xx/429) вызовы к провайдеру автоматически временно заменяются на локальную заглушку или резервный регион [200].
2. **Идемпотентность инструментов (Idempotency Keys)**: Каждый вызов деструктивного или финансового инструмента должен сопровождаться уникальным ключом идемпотентности (`idempotency_key`), предохраняющим от повторного списания при сетевом сбое [200].
3. **Стратегии обработки сбоев**:
   * **Fail Closed**: Блокировка операции при сбое (банковские операции) [195, 197].
   * **Fail Open**: Пропуск операции с логированием (некритичные рекомендательные системы) [196].
   * **Graceful Degradation**: Переход на детерминированный алгоритм/шаблон при недоступности LLM [196, 198].

---

### 7.3. Сквозная наблюдаемость (Observability) и 5 ключевых метрик AI-агентов
Классический мониторинг (HTTP 200/500) бесполезен для AI-агентов, так как система может возвращать код 200, уничтожая бюджет в бесконечном цикле [205, 206].

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      5 CRITICAL AGENTIC METRICS                         │
├─────────────────────────────────────────────────────────────────────────┤
│ 1. Tool Call Success Rate (по каждому тулу отдельно)             [211]  │
│ 2. Semantic Loop Distance (дистанция в эмбеддинг-пространстве)   [212]  │
│ 3. Context Utilization & Compaction Frequency                     [213]  │
│ 4. Tool Selection Accuracy (точность выбора инструмента)         [215]  │
│ 5. Total Cost per Task Execution (суммарный TCO задачи)          [216]  │
└─────────────────────────────────────────────────────────────────────────┘
```

1. **Tool Call Success Rate**: Процент успешных вызовов инструментов, измеряемый отдельно по каждому тулу [211].
2. **Semantic Loop Distance**: Измерение расстояния в пространстве эмбеддингов между последовательными вызовами инструментов. Если расстояние ниже порога — агент в цикле-галлюцинации [212, 213].
3. **Context Utilization & Compaction Frequency**: Частота срабатывания уплотнения контекста. Высокая частота указывает на риск потери системных инструкций [213, 214].
4. **Tool Selection Accuracy**: Оценка релевантности выбранных инструментов целевому запросу [215].
5. **Total Cost per Task Execution (TCO задачи)**: Суммарная стоимость всех итераций, токенов и вызовов API в рамках одной бизнес-задачи [216].

---

### 7.4. Заключение: Чек-лист готовности к деплою
Перед выпуском AI-агента в продакшен убедитесь, что выполняются следующие условия:

- [ ] Лимиты итераций цикла и бюджета токенов зафиксированы **в коде**, а не в промпте [35].
- [ ] Все неинвариантные действия с высокой ответственностью защищены **Human-in-the-Loop** [35, 182].
- [ ] Все инструменты принимают **ключи идемпотентности** [200].
- [ ] Настроено трассирование сессий с отслеживанием метрики **Cost per Task** [216].
- [ ] Реализован **Circuit Breaker** и алгоритм ретраев с экспоненциальной задержкой (Exponential Backoff + Jitter) [136, 200].
- [ ] Дисциплина записи баз знаний переведена в режим **Append-Only** с проверкой источников [106, 112].

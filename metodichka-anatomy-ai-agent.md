## Модуль 1. Анатомия AI-агента: пайплайн, цикл, инструменты, ловушки

> Развёрнутая версия модуля с примерами, кодом и упражнениями — [Глава 1 учебника](textbook/01-anatomy-of-an-ai-agent.md), код — [`code/ch01/`](code/ch01/).

### 1.1. Прототип vs продакшен
Агента на LangChain, AutoGen или CrewAI можно собрать в несколько строк, но в продакшене система сталкивается с неконтролируемыми расходами, бесконечными циклами и непредсказуемым поведением.

* **DataTalks.Club (февраль 2026)**: Claude Code выполнил `terraform destroy` и удалил продакшен-инфраструктуру курсов вместе с автоматическими снапшотами (~2,5 года работ студентов). Причина — цепочка инженерных ошибок: state-файл Terraform не был перенесён, агент подменил state архивной копией, человек не остановил `destroy`. Данные восстановили через сутки с помощью поддержки AWS.
* **Gartner (июнь 2025)**: более 40% проектов агентного ИИ будут закрыты к концу 2027 года из-за затрат, неясной ценности и слабого контроля рисков.
* В видео также приводятся счёт ~\$2,5 млн/мес. против \$50 на прототипе и бот, повторивший ответ 58 раз подряд *(первоисточники не указаны)*.

> **Главный тезис**: проблема не в модели, а в инженерии вокруг неё. Успешные системы строятся на простых компонуемых паттернах и жёстком коде, а не на «магических» фреймворках.

---

### 1.2. Workflow vs Agent: лестница усложнения
* **Workflow («рельсы»)**: последовательность шагов задаёт код, LLM выполняет шаг, но **не выбирает следующий**. Максимум контроля и предсказуемости, минимальная цена.
* **Agent («автономия»)**: модель сама выбирает инструмент и следующий шаг. Гибкость ценой стоимости, задержки и риска ошибок.

| # | Уровень | Суть |
| :--- | :--- | :--- |
| 1 | Single LLM Call | Один запрос — один ответ. Если хватает — усложнять нельзя |
| 2 | Prompt Chaining | Выход шага N — вход шага N+1; здесь же встраивается Human-in-the-Loop |
| 3 | Routing | Быстрый дешёвый классификатор направляет запрос в специализированную цепочку |
| 4 | Parallelization | Независимые подзадачи выполняются одновременно |
| 5 | Orchestrator–Workers | LLM-оркестратор декомпозирует задачу и раздаёт её исполнителям |
| 6 | ReAct Agent | Модель сама планирует, выбирает инструменты и крутится в цикле до результата |
| 7 | Multi-Agent System | Несколько агентов работают командой (см. Модуль 5) |

Уровни 1–5 — workflow, 6–7 — агенты. В статье Anthropic «Building effective agents» к паттернам workflow относится также **Evaluator–Optimizer** (генерация + оценка в цикле).

> **Золотое правило**: увеличивайте автономию только тогда, когда workflow не справляется с вариативностью задачи.

---

### 1.3. Системный промпт как контракт
Системный промпт — архитектурный контракт поведения: он версионируется и тестируется как код (eval-набор из типичных и «злых» запросов). Четыре обязательные секции:

1. **Роль и явные границы** — что агент делает и чего не делает.
2. **Приоритизированные правила** — нумерованный список; при конфликте: безопасность > бюджет > удобство.
3. **Формат ответа** — JSON-схема, Markdown и т. п.
4. **Пример (few-shot)** — диалог-образец.

Динамических данных (время, имя пользователя) в системном промпте нет — они ломают KV-кэш (п. 1.5).

---

### 1.4. Пайплайн: «Блокируй рано, трать поздно»
Дешёвые проверки — первыми, дорогой вызов LLM — как можно позже. Любой этап может прервать обработку.

```
[Запрос]
  1. Validation ($0) ─────────────► отказ: пусто / мусор / слишком длинно
  2. Input Security ──────────────► отказ: prompt injection
  3. Context Enrichment             (календарь, задачи, состояние)
  4. Memory & Retrieval             (предпочтения, RAG)
  5. Content Filtering ───────────► выброс: битые документы, утечки, непрямые инъекции
  6. Context Assembly & Budgeting   (greedy / суммаризация / compaction)
  7. Smart Routing & Mode           (дешёвая/дорогая модель, Thinking Mode)
  8. Generation                     (вызов LLM / Agent Loop)
  9. Output Security ─────────────► блок: PII, утечка системного промпта (canary-токен)
 10. Formatting & Validation ─────► повтор / ошибка: невалидный JSON
[Ответ]
```

* Найденные документы и **ответы инструментов** — недоверенный ввод: непрямая prompt injection приходит через них, поэтому проверки на этапе 2 недостаточно.
* В описании видео заявлено 12 этапов, в расшифровке перечислено 10; этапы можно объединять и дробить — важен порядок «дёшево → дорого».

---

### 1.5. Экономика кэширования: KV-кэш
* В цикле агента модель на каждой итерации перечитывает весь контекст; соотношение входных и выходных токенов — порядка 100:1 (оценка Manus).
* KV-кэш (prompt caching) удешевляет повторно читаемый префикс примерно в 10 раз — **только если префикс не изменился**.
* Без кэша стоимость задачи растёт квадратично от числа шагов (на шаге *i* читается ~*i·k* токенов).

**Что убивает кэш**: время в начале системного промпта; изменение середины контекста; нестабильный порядок ключей в JSON.

> **Правило**: статичное — в начало, динамичное — в конец; в цикле данные только добавляются в конец; JSON сериализуется со стабильным порядком ключей.

---

### 1.6. Защита Agent Loop в коде
Риски незащищённого цикла: зацикливание, взрыв стоимости, каскад галлюцинаций (ошибка шага N становится «фактом» для шага N+1).

Барьеры внедряются **в коде, а не в промпте**:

1. **Лимит итераций** — например, ~5 для поддержки, ~25 для кодинга.
2. **Бюджет токенов** на задачу/сессию.
3. **Лимит одинаковых вызовов инструмента подряд** (имя + аргументы). Повтор после таймаута или опрос статуса — не всегда ошибка, поэтому считаются именно идентичные вызовы.
4. **Human-in-the-Loop** перед необратимыми действиями (удаление, платёж, отправка письма): цикл приостанавливается с сохранением состояния и продолжается после ответа человека.
5. **Лимит времени** на задачу и **таймаут** на каждый инструмент *(дополнение к видео)*.

При срабатывании лимита модель получает конструктивную инструкцию, а не абстрактную ошибку: «Инструмент вызывался 4 раза, данные собраны, сформируй финальный ответ сейчас». После этого инструменты ей больше не передаются.

---

### 1.7. Проектирование инструментов и ловушка MCP
* **Количество**: при росте числа инструментов (порядка 20–50) начинается «смерть от тысячи инструкций» — границы размываются, модель путает инструменты.
* **Описание**: имя `глагол_существительное` (`get_user_preferences`), позитивные инструкции «что и когда делать», строгая JSON-схема и значения по умолчанию.
* **Ошибки как инструкции**: не `500 Internal Server Error`, а объяснение, что произошло и как скорректировать следующий шаг.
* **Ловушка автоматических MCP-обёрток**: автогенерация MCP-сервера из API работает только для happy path — без обработки таймаутов, специфичных ошибок и пометки опасных операций система ломается в продакшене. Инструменты проектируются под задачи агента, а не по эндпоинтам.

### 1.8. Наблюдаемость с первого дня
Наблюдаемость отвечает на вопрос, почему запрос стоил \$12 вместо \$0,02 и занял 8 секунд. С первого дня логируются: начало и конец каждого этапа пайплайна, выбор модели и версия промпта, итерации цикла и токены, параметры и ответы инструментов, **KV Cache Hit Rate**, итоговая стоимость запроса. *(Подробнее — Модуль 7.3.)*

## Модуль 2. Архитектура интеллекта и памяти AI-агента

### 2.1. Классификация 4 типов памяти по фреймворку CoALA
В соответствии с фреймворком CoALA (Cognitive Architectures for Language Agents, Принстон, 2023), память AI-агента разделяется на 4 специализированных слоя с различным жизненным циклом:

```
+--------------------+--------------------+-------------------------------+-------------------------------+
|                                     AI AGENT MEMORY                                                   |
+--------------------+--------------------+-------------------------------+-------------------------------+
| Процедурная        | Семантическая      | Эпизодическая                 | Рабочая                       |
| (Procedural)       | (Semantic)         | (Episodic)                    | (Working)                     |
+--------------------+--------------------+-------------------------------+-------------------------------+
| System Prompt,     | Базы знаний, RAG,  | Дневник уроков, прошлый опыт  | Текущее контекстное окно,     |
| инструкции тулов   | факты о проекте    | успехов и ошибок              | состояние активной задачи     |
| Меняется редко     | Накапливается      | Обогащает действия контекстом | Очищается после завершения    |
+--------------------+--------------------+-------------------------------+-------------------------------+
```

1. **Процедурная память (Procedural Memory)**: Знание того, *как выполнять задачи*. Включает системный промпт, правила валидации, контракты вызова инструментов. Изменяется разработчиком между сессиями.
2. **Семантическая память (Semantic Memory)**: Знание *фактов и мира*. Представляет собой внешние базы знаний, векторные хранилища (RAG) и документацию.
3. **Эпизодическая память (Episodic Memory)**: Опыт *прошлых действий и уроков*. Хранит записи вида: `[Контекст] -> [Действие] -> [Результат] -> [Извлеченный урок]`. Позволяет агенту не повторять вчерашние ошибки. *(Изучите реализацию в [Модуле 6.3](#63-фоновый-агент-арбитр-wikigroomer-и-борьба-с-концепт-дрифтом)).*
4. **Рабочая память (Working Memory)**: Оперативный контекст текущей задачи. Ограничена размером контекстного окна и полностью очищается/суммаризируется по завершении сессии.

---

### 2.2. Сравнительный анализ: RAG vs. Длинное контекстное окно
С появлением моделей с контекстным окном в 1-2 млн токенов возникло заблуждение, что RAG больше не нужен. Инженерный анализ показывает жесткие компромиссы:

| Критерий | RAG (Retrieval-Augmented Generation) | Long Context Window (1M+ токенов) |
| :--- | :--- | :--- |
| **Сложность инфраструктуры** | Высокая (векторные базы, чанкинг, эмбеддинги, реранкинг) | Минимальная (загрузка всего файла напрямую в промпт) |
| **Стоимость эксплуатации** | Низкая (оплата только релевантных чанков) | Высокая: весь документ оплачивается при каждом вызове (KV-кэш снижает, но не устраняет) |
| **Точность локального поиска** | Высокая (извлечение точных «иголок» без шума) | Уязвима к эффектам *Lost in the Middle* и *Context Erosion* |
| **Полнота глобального анализа** | Риск упустить связи при разрыве чанков | Абсолютная (модель видит весь документ целиком) |

> **Производственный стандарт**: Гибридный подход. RAG используется для первичной фильтрации базы знаний из гигабайт до десятков тысяч токенов, которые затем подаются в контекст для глубокого рассуждения.

---

### 2.3. Стратегическое мышление (Thinking Mode) и бюджетирование токенов
Режим глубокого рассуждения (Thinking / Reasoning Mode) генерирует внутреннюю цепочку мыслей перед выдачей ответа.

* **Экономический фактор**: Токены рассуждения (Thinking Tokens) тарифицируются как *выходные токены*, которые у большинства провайдеров стоят в **4–5 раз (и более) дороже входных**.
* **Динамический Reasoning**:
  * Простые семантические запросы («Сколько стоит доставка?») → *Thinking Disabled* (Дешёвая модель).
  * Сложный архитектурный анализ или первичная декомпозиция задачи → *Thinking Enabled* на первых 1-2 итерациях цикла, с последующим отключением режима для рутинных вызовов инструментов. *(См. [Модуль 3.3](#33-гибридный-роутинг-и-архитектура-классификаторов)).*

## Модуль 3. Экономика и выбор LLM в продакшене

### 3.1. Стратегический выбор: API vs. Self-Hosted (Open-Source)
Выбор между провайдерами API (Anthropic, OpenAI, Google) и собственным хостингом Open-Source моделей (Llama, Qwen, DeepSeek) определяется тремя векторами:

```
                         [Требования к регуляции и PII]
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
           [Да / Строгие]                            [Нет / Гибкие]
                 │                                         │
        [Запрет облаков?]                         [Расчет TCO & Масштаб]
           ┌─────┴─────┐                             ┌─────┴─────┐
           ▼           ▼                             ▼           ▼
      [Self-Host]  [Enterprise API]             [Self-Host]    [API]
```

1. **Регуляторные ограничения (Data Privacy)**: При наличии требований ФЗ/GDPR/HIPAA и невозможности использования изолированных Enterprise VPC — выбор однозначно за Self-Host.
2. **Нагрузка и паттерн трафика**: На малых и средних объемах API, как правило, дешевле за счет отсутствия простоев выделенного GPU.
3. **Потребность в тонкой настройке (Fine-tuning)**: Если под узкий домен требуется специфический формат вызова инструментов или специальный язык, выигрывает Open-Source.

---

### 3.2. Расчет совокупной стоимости владения (TCO)
При сравнении стоимости **нельзя сравнивать только цену токенов API со стоимостью аренды GPU**. Реальная формула TCO для Self-Hosted включает 4 компонента:

```
TCO(Self-Host) = Cost(GPU) + Cost(Infra) + Cost(DevOps/SRE) + Cost(Complexity)
```

* **Cost GPU**: Прямая аренда карт (A100/H100) или кластеров.
* **Cost Infra**: Трафик, хранилище для весов и векторных БД.
* **Cost DevOps/SRE**: Зарплатные часы высококвалифицированных инженеров на настройку vLLM/TGI, оптимизацию квантования и поддержку SLA 99.9%. *Часто эта статья в 5-10 раз превышает арендную плату за GPU.*
* **Cost Complexity**: Издержки от задержки выкатки новых фич.

---

### 3.3. Гибридный роутинг и архитектура классификаторов
Для оптимизации затрат без потери качества применяется **гибридная архитектура роутинга** (Router LLM):

```
[Запрос пользователя] ──► [Классификатор (Small Model / Fast Classifier)]
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
 [Простой запрос]          [Средняя сложность]       [Сложный / Критичный]
  Малая / локальная модель     Средняя модель           Фронтир-модель
     (Стоимость: 1x)          (Стоимость: ~10x)        (Стоимость: ~50x+)
```

1. **Классификатор (Router)**: Быстрый классификатор или малая модель (≈1–3B параметров) за миллисекунды оценивает сложность входящего запроса.
2. **Таблицы маршрутизации**: Простые CRUD-операции и стандартные вопросы направляются на локальные/дешёвые модели. Многошаговое рассуждение и генерация кода — на топовые фронтир-модели.
3. **Учет KV-Cache при роутинге**: Внимательно отслеживайте смену моделей внутри одного диалога. Переключение модели посреди длинного чата инвалидирует KV-кэш предыдущей модели, что ведет к повторным затратам.

## Модуль 4. Harness Engineering: проектирование среды исполнения

### 4.1. Парадигмальный сдвиг: От промпт-инжиниринга к Harness Engineering
> *«Качество работы агента определяет не столько сама модель, сколько код обвязки (Harness) вокруг неё».*

Промпт-инжиниринг как отдельная дисциплина исчерпал себя. На смену пришел **Harness Engineering** — проектирование надежной среды исполнения, алгоритмов верификации и автоматических обратных связей.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        HARNESS ENGINEERING LAYER                       │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────────┐  │
│  │    Constrain     │  │      Inform      │  │        Verify        │  │
│  │ (Ограничения)    │  │ (Информирование) │  │    (Верификация)     │  │
│  └────────┬─────────┘  └────────┬─────────┘  └──────────┬───────────┘  │
│           │                     │                       │              │
│           └─────────────────────┼───────────────────────┘              │
│                                 ▼                                      │
│                      ┌──────────────────────┐                          │
│                      │       Correct        │                          │
│                      │  (Коррекция/Retry)   │                          │
│                      └──────────────────────┘                          │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   ▼
                      [LLM / Двигатель системы]
```

---

### 4.2. 4 управляющие функции (OpenAI Framework)
> *Атрибуция по курсу; схема перекликается с публикацией OpenAI «Harness engineering» (2026), точные формулировки стоит сверить с первоисточником.*

Обвязка агента выполняет 4 ключевые функции:

1. **Constrain (Ограничить)**: Программное установление рамок — жесткие лимиты токенов, списки разрешенных вызовов (allowlists), песочницы исполнения.
2. **Inform (Проинформировать)**: Передача контекста, инструкций к инструментам и динамического состояния системы.
3. **Verify (Проверить)**: Автоматическая проверка результатов работы агента через инварианты, линтеры и тесты.
4. **Correct (Исправить)**: Автоматическое формирование конструктивных сообщений об ошибках и возврат агента на повторную итерацию цикла.

---

### 4.3. 7 слоев системной обвязки (Harness Architecture)
Современная производственная обвязка делится на 7 функциональных слоев:

1. **Execution Sandbox (Ядро исполнения)**: Изолированная среда (Docker, gVisor, WASM) для выполнения кода и команд агентом.
2. **Tooling & Protocols (Инструментальный слой)**: Валидация схем инструментов (JSON Schema, MCP Protocol), обработка тайм-аутов и гармонизация ошибок.
3. **Context Manager (Управление контекстом)**: Сборка промпта, отсечение устаревших данных, стратегии уплотнения (Compaction).
4. **Lifecycle & State Machine (Управление жизненным циклом)**: Оркестрация состояний, обработка прерываний, возобновление сессий (Recovery).
5. **Observability Layer (Слой наблюдаемости)**: Сквозное трассирование, метрики, логирование шагов и вызовов. *(См. [Модуль 7.3](#73-сквозная-наблюдаемость-observability-и-5-ключевых-метрик-ai-агентов)).*
6. **Verification Layer (Слой проверки)**: Инварианты в коде, Judge-модели, замеры качества.
7. **Governance & Security (Слой безопасности)**: Защита от Prompt Injection, разграничение прав доступа, лимиты суточных бюджетов.

---

### 4.4. Трехуровневая верификация инвариантов
Проверка результатов агента выстраивается в иерархию по скорости и стоимости:

```
Level 1: Invariants in Code (0$ / 0ms) ──► Мгновенная проверка детерминированными правилами
Level 2: Benchmark & Evaluation Runs  ──► Периодические запуски на эталонных датасетах
Level 3: Human-in-the-Loop Validation ──► Проверка человеком сложных и рискованных действий
```

* **Level 1: Инварианты в коде (Invariants in Code)**: Мгновенные, бесплатные проверки. *Пример*: Сумма возврата не может превышать сумму заказа; дата релиза не может быть в прошлом.
* **Level 2: Замеры на эталонных запросах (Eval Runs)**: Автоматический прогон системных тестов при смене модели или обновлении промптов.
* **Level 3: Проверка человеком (Human-in-the-Loop)**: Подтверждение критических действий.

## Модуль 5. Мультиагентные системы и архитектурные паттерны

### 5.1. Природа когнитивной перегрузки одиночной модели
Передача единой сложной задачи («Проведи аудит кода, найди баги, перепиши модули, обнови документацию и составь отчет») одной моделью приводит к **когнитивной перегрузке** (Cognitive Overload).
* Модель размывает внимание между десятками инструкций (*Loss of Focus*).
* Возрастает вероятностная ошибка при выборе из большого количества инструментов (при числе инструментов больше ~20 начинается резкое падение точности).

*Решение*: Разделение труда и специализация — построение мультиагентной команды, где каждый агент обладает узким контекстом и ограниченным набором инструментов.

---

### 5.2. 7 ключевых паттернов мультиагентного взаимодействия
В индустрии сформировались 7 фундаментальных архитектурных паттернов:

```
1. Pipeline        : [A1] ──► [A2] ──► [A3]
2. Router          : [Router] ──► [A_fast] OR [A_expert]
3. Parallelization : [A_split] ──► [A1] + [A2] + [A3] ──► [Aggregator]
4. Reflection      : [Generator] ◄──► [Critic / Reflector]
5. Tool Use        : [Agent] ──► [Orchestrator] ──► [External APIs]
6. Planning        : [Planner] ──► [Task Graph] ──► [Workers]
7. Collaboration   : [Role A] ◄──► [Role B] ◄──► [Role C] (Shared Environment)
```

1. **Pipeline Pattern (Конвейер)**: Последовательная передача выхода одного агента на вход следующему. *Применение*: Пошаговая обработка документов.
2. **Router Pattern (Маршрутизатор)**: Первичный агент определяет категорию задачи и направляет её узкоспециализированному агенту.
3. **Parallelization Pattern (Параллелизация)**: Декомпозиция независимых подзадач и их одновременное выполнение с последующей агрегацией. *Применение*: Анализ больших объемов данных.
4. **Reflection Pattern (Рефлексия)**: Пара «Генератор — Критик». Критик оценивает вывод генератора по критериям качества и возвращает на доработку до достижения идеала.
5. **Tool Use Pattern (Использование инструментов)**: Оркестрация вызовов внешних функций и API с валидацией возвращаемых ответов.
6. **Planning Pattern (Планирование)**: Планировщик строит динамический граф задач (Task Graph), который исполняется рабочими воркерами.
7. **Collaboration Pattern (Коллаборация)**: Команда агентов с разными ролями (например, Программист, Тестировщик, PM) взаимодействует в общей среде до решения задачи.

---

### 5.3. Накладные расходы, антипаттерны и принцип прогрессивной сложности
Переход к мультиагентным системам сопровождается существенными издержками:
* **Рост потребления токенов**: По данным Anthropic, мультиагентная исследовательская система расходует **~15× больше токенов, чем обычный чат** (одиночный агент — ~4×), т. е. примерно в 3–4 раза больше одиночного агента.
* **Рост задержки (Latency)**: Сетевые вызовы и последовательное согласование между агентами увеличивают время отклика.

#### Антипаттерны применения:
* Использование мультиагентных команд для простых FAQ или линейных задач.
* Избыточная координация для систем реального времени.

> **Принцип прогрессивной сложности**: *Начинайте с одного агента -> Добавляйте рефлексию -> Внедряйте роутинг -> Переходите к параллелизации и планированию только при исчерпании возможностей предыдущих ступеней.*

## Модуль 6. Долговременная память и управление знаниями

### 6.1. Архитектурная развилка: Синтез при записи vs. Синтез при чтении
При проектировании баз знаний для AI-агентов существует фундаментальная развилка:

```
                    [ВХОДЯЩИЕ ДАННЫЕ / ИСТОЧНИКИ]
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
[Синтез при записи (Write-Time)]               [Синтез при чтении (Read-Time)]
- Агент обобщает факты СРАЗУ.                  - Данные сохраняются в СЫРОМ виде.
- Запись дорогая, чтение дешёвое.              - Запись бесплатная, чтение дорогое.
- РИСК: Сжатие с потерями и искажения.         - ПЛЮС: Полная сохранность оригинала.
```

---

### 6.2. Дисциплина записи: Append-Only журналы и якоря происхождения
Главная причина «порчи» памяти при наличии нескольких агентов-писателей — перезапись файлов (*Lost Update* / *Write Collisions*).

#### Производственные стандарты дисциплины записи:
1. **Append-Only Log (Журнал только для записи)**: Никакой агент не имеет права редактировать или удалять прошлые записи в БД. Новая информация добавляется строго инкрементально в конец.
2. **Якоря происхождения (Source Anchoring)**: Каждая запись в памяти должна содержать привязку к неизменяемому первоисточнику (ID транскрипта, хэш коммита, URL документа, timestamp).

---

### 6.3. Фоновый агент-арбитр (WikiGroomer) и борьба с концепт-дрифтом
Со временем факты в базе знаний устаревают и начинают противоречить друг другу (Концепт-дрифт). Для поддержания гигиены памяти выделяется специальный фоновый процесс — **WikiGroomer**:

#### Задачи агента WikiGroomer:
1. **Консолидация и дедупликация**: Периодическое прочесывание сырого лога и сборка аккуратных сводок-кэшей.
2. **Детекция противоречий**: Нахождение конфликтующих фактов (например, «Используем GitFlow» vs «Перешли на Trunk-Based Development») и их эскалация человеку в командный чат.
3. **Версионирование актуальности**: Старые записи не удаляются, а закрываются с проставлением даты окончания актуальности (`valid_to`).

---

### 6.4. Проблема отравления памяти (Memory Poisoning) и Prompt Injection
Общая память представляет собой поверхность атаки. Если один из агентов прочитал вредоносный сайт или отравленное письмо (Indirect Prompt Injection), он может записать инструкции атаки в общую память.

#### Защитный принцип «Правило двух» (Meta, Agents Rule of Two) и «смертельная триада» (S. Willison):
Опасность возникает при одновременном наличии трёх условий:  
1. Доступ к приватным данным.  
2. Недоверенный входной поток.  
3. Канал вывода информации наружу.

> **Защита**: в одной сессии агент должен обладать не более чем **двумя** из трёх свойств. Разорвите цепочку, заблокировав канал вывода наружу (Human-in-the-Loop) при контакте агента с немодерируемой памятью. *(См. [Модуль 7.1](#71-многоуровневая-безопасность-defense-in-depth-и-избыточная-автономия)).*

## Модуль 7. Продакшн-эксплуатация: безопасность, отказоустойчивость и наблюдаемость

### 7.1. Многоуровневая безопасность (Defense-in-Depth) и избыточная автономия
Атаки на AI-агентов выходят за рамки обычной веб-безопасности:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      DEFENSE-IN-DEPTH ARCHITECTURE                      │
│                                                                         │
│  [Вход] ──► 1. Input Security Gate (Guard Models)                       │
│                   │                                                     │
│                   ▼                                                     │
│             2. Content & RAG Integrity Verification (Hashes & Evals)    │
│                   │                                                     │
│                   ▼                                                     │
│             3. Isolated Execution Sandbox (e.g. gVisor / Docker)        │
│                   │                                                     │
│                   ▼                                                     │
│             4. Output Validation & Human Gate ──► [Выход]               │
└─────────────────────────────────────────────────────────────────────────┘
```

#### Риск избыточной автономии (Excessive Agency / Confused Deputy):
Ситуация, когда агент обладает полномочиями выполнения опасных команд, но теряет понимание границ в процессе работы.

#### Стратегия защиты:
* **Изоляция прав (Least Privilege)**: Агент должен иметь доступ только к микро-токенам с минимально необходимыми правами.
* **Программный Proxy**: Проверка опасности тула выполняется внешним кодом прокси-сервера, а не инструкцией в промпте.

---

### 7.2. Отказоустойчивость (Resilience): Circuit Breakers, идемпотентность и стратегия ошибок
Производственный агент должен сохранять работоспособность при падении внешних LLM-провайдеров:

1. **Circuit Breaker (Предохранитель)**: При превышении порога ошибок (5xx/429) вызовы к провайдеру автоматически временно заменяются на локальную заглушку или резервный регион.
2. **Идемпотентность инструментов (Idempotency Keys)**: Каждый вызов деструктивного или финансового инструмента должен сопровождаться уникальным ключом идемпотентности (`idempotency_key`), предохраняющим от повторного списания при сетевом сбое.
3. **Стратегии обработки сбоев**:
   * **Fail Closed**: Блокировка операции при сбое (банковские операции).
   * **Fail Open**: Пропуск операции с логированием (некритичные рекомендательные системы).
   * **Graceful Degradation**: Переход на детерминированный алгоритм/шаблон при недоступности LLM.

---

### 7.3. Сквозная наблюдаемость (Observability) и 5 ключевых метрик AI-агентов
Классический мониторинг (HTTP 200/500) бесполезен для AI-агентов, так как система может возвращать код 200, уничтожая бюджет в бесконечном цикле.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      5 CRITICAL AGENTIC METRICS                         │
├─────────────────────────────────────────────────────────────────────────┤
│ 1. Tool Call Success Rate (по каждому тулу отдельно)                    │
│ 2. Semantic Loop Distance (дистанция в эмбеддинг-пространстве)          │
│ 3. Context Utilization & Compaction Frequency                           │
│ 4. Tool Selection Accuracy (точность выбора инструмента)                │
│ 5. Total Cost per Task Execution (суммарный TCO задачи)                 │
└─────────────────────────────────────────────────────────────────────────┘
```

1. **Tool Call Success Rate**: Процент успешных вызовов инструментов, измеряемый отдельно по каждому тулу.
2. **Semantic Loop Distance**: Измерение расстояния в пространстве эмбеддингов между последовательными вызовами инструментов. Если расстояние ниже порога — агент в цикле-галлюцинации.
3. **Context Utilization & Compaction Frequency**: Частота срабатывания уплотнения контекста. Высокая частота указывает на риск потери системных инструкций.
4. **Tool Selection Accuracy**: Оценка релевантности выбранных инструментов целевому запросу.
5. **Total Cost per Task Execution (TCO задачи)**: Суммарная стоимость всех итераций, токенов и вызовов API в рамках одной бизнес-задачи.

---

### 7.4. Заключение: Чек-лист готовности к деплою
Перед выпуском AI-агента в продакшен убедитесь, что выполняются следующие условия:

- [ ] Лимиты итераций цикла и бюджета токенов зафиксированы **в коде**, а не в промпте.
- [ ] Все необратимые действия с высокой ответственностью защищены **Human-in-the-Loop**.
- [ ] Все инструменты с побочными эффектами (платежи, запись, отправка) принимают **ключи идемпотентности**.
- [ ] Настроено трассирование сессий с отслеживанием метрики **Cost per Task**.
- [ ] Реализован **Circuit Breaker** и алгоритм ретраев с экспоненциальной задержкой (Exponential Backoff + Jitter).
- [ ] Системный промпт версионируется и покрыт eval-тестами; KV Cache Hit Rate отслеживается.
- [ ] Дисциплина записи баз знаний переведена в режим **Append-Only** с проверкой источников.
